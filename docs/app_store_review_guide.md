# iOSアプリ開発・App Store審査の教訓
## Futoの審査経験に基づく開発エージェント向けガイドライン

### 1. 基本方針

本プロジェクトでは、FutoアプリのApp Store審査で発生した問題を教訓として、開発初期からAppleの審査要件を満たす設計・実装を行うこと。

**最重要原則**

- アプリが動作するだけでなく、App Storeで公開できる状態までを完成とする。
- Appleの審査ガイドライン、署名、プライバシー、課金、メタデータを開発段階から考慮する。
- 審査直前になって大規模な設計変更が必要になる状況を避ける。
- SDKの導入によって発生するプライバシー要件も確認する。
- 審査担当者がアプリの機能を実際に試せる状態を用意する。
- 自動テストの成功だけで審査通過を保証しない。
- 審査ガイドラインは変更されるため、提出時点の公式資料を確認する。

---

### 2. 実際に発生した問題と教訓

#### 2.1 Privacy Manifestの不整合（ITMS-91064）

**発生した問題**

Futoの初期ビルドで、Privacy Manifestに関する検証エラーが発生した。

Google Mobile Ads SDKを含むアプリのプライバシー申告と、実際のSDK構成・Privacy Manifestの整合性が問題となった。

**教訓**

外部SDKを導入した場合、アプリ自身のコードだけでなく、SDKが扱うデータや追跡機能まで確認する必要がある。

**今後の対策**

- `PrivacyInfo.xcprivacy` の内容を確認する。
- SDKが収集するデータの種類と利用目的を調査する。
- XcodeのPrivacy Reportを確認する。
- App Store Connectのプライバシー申告と整合させる。
- Trackingに該当する場合はATTへの対応を検討する。
- ATTを使用しない場合も、実際に追跡が発生しない構成であることを確認する。
- SDK更新時にはプライバシー要件を再確認する。

**禁止事項**

審査エラーを消す目的だけで、実態に合わないTracking設定やドメインをPrivacy Manifestに追加しないこと。

#### 2.2 Family Controlsの権限・署名エラー

**発生した問題**

FutoではScreen Time APIを使用していたが、Appleの自動検証でFamily Controlsの権限不足を指摘された。

Futoには以下の複数ターゲットが存在していた。

- メインアプリ
- Device Activity Monitor Extension
- Shield Configuration Extension
- Shield Action Extension

**教訓**

Appleの特別な権限を必要とするAPIでは、メインアプリだけでなく、関連するExtensionを含めた権限設定が必要になる。

**今後の対策**

- 使用するAPIに特別なEntitlementが必要か事前調査する。
- DevelopmentとDistributionの権限を区別する。
- App IDごとに必要なCapabilityを設定する。
- Provisioning Profileを更新する。
- Release Archiveの署名済みEntitlementsを検証する。
- Extensionを含む全ターゲットを確認する。
- 実機で動作確認する。

**重要**

XcodeのDebugビルドで動作することは、App Store配布用の署名が正しいことを意味しない。

#### 2.3 自動更新サブスクリプションの却下（Guideline 3.1.2）

**発生した問題**

Futoでは当初、次の月額課金を用意していた。

- 広告なし：月150円
- 応援：月500円

しかしAppleから、自動更新サブスクリプションとして適切ではないと判断された。

広告削除や単純な開発者支援だけでは、継続的な価値提供として認められない場合がある。

**実施した方針変更**

- 広告削除：買い切り型の非消耗型課金
- 開発者支援：消耗型課金

**今後の対策**

課金方式は開発初期に決定する。

| 課金内容 | 基本的な選択 |
|---|---|
| 広告の永久削除 | 非消耗型 |
| 機能の永久解放 | 非消耗型 |
| 単発の応援・チップ | 消耗型 |
| 継続的なサービス提供 | 自動更新サブスクリプション |
| 期間限定のサービス利用 | 内容に応じて適切な課金方式を選択 |

サブスクリプションを採用する場合は、継続的な価値、更新条件、解約方法などを明確にする。

課金方式の変更はStoreKit実装、商品ID、購入復元、UI、App Store Connect設定に影響するため、後回しにしない。

#### 2.4 利用規約（EULA）の不足

**発生した問題**

自動更新サブスクリプションを設定した際、App Storeの商品ページに必要な利用規約へのリンクが不足していた。

**今後の対策**

- 課金モデルに応じて必要な利用規約を用意する。
- 自動更新サブスクリプションでは、利用規約とプライバシーポリシーを適切に表示する。
- Apple標準EULAまたは独自EULAを正しく設定する。
- 日本語・英語など各ローカライズのメタデータを確認する。
- アプリ内からも必要な情報にアクセスできるようにする。

#### 2.5 権限要求画面の表現（Guideline 5.1.1）

**発生した問題**

Screen Time権限を要求する前の独自画面で、許可を誘導する表現が問題になった。

Futoでは、許可前のボタンを「許可する」から「次へ」に変更するなどの修正を行った。

**教訓**

権限取得前の画面は、ユーザーが内容を理解するための説明画面であり、許可を強制・誘導する画面ではない。

**今後の対策**

- 権限を必要とする理由を中立的に説明する。
- システムの許可ダイアログと独自画面を混同させない。
- 許可前のボタンは「次へ」など実際の操作に即した表現にする。
- 拒否した場合も威圧的な文言を表示しない。
- 権限がなくても利用可能な機能を明確にする。
- 許可を得るための誤解を招くUIを作らない。

#### 2.6 年齢レーティングの設定ミス（Guideline 2.3.6）

**発生した問題**

App Store Connectの年齢レーティングで「In-App Controls」を設定していたが、審査側から該当する機能が確認できないと指摘された。

**今後の対策**

- 年齢レーティングの回答は実際の機能に基づいて設定する。
- Appleの各項目の定義を確認する。
- 類似する機能名だけで判断しない。
- 審査担当者が確認しづらい機能はReview Notesで説明する。
- 該当しない項目を念のため有効にすることは避ける。

#### 2.7 ログイン機能と審査用アクセス

**発生した問題・懸念**

Futoでは基本機能がログイン不要である一方、共有・フレンド機能ではAppleまたはGoogleログインを使用していた。

審査担当者がこれらの機能を試せるかが課題となった。

**実施した対策**

審査用デモモードを実装し、外部認証なしでも共有・フレンド機能を確認できるようにした。

**今後の対策**

- ログイン必須か任意かを明確にする。
- 審査対象機能にアクセスできる方法を用意する。
- 必要に応じて審査用アカウントまたはデモモードを提供する。
- Review Notesに具体的な操作手順を記載する。
- デモモードが実際の機能を誤認させないようにする。
- 審査担当者に個人アカウントの作成を要求しない設計を検討する。

#### 2.8 バージョン番号とアップロードエラー

**発生した問題**

承認済みのバージョン1.0に対し、再び1.0としてアップロードしようとして以下のエラーが発生した。

- `CFBundleShortVersionString` must contain a higher version
- `Invalid Pre-Release Train`

**教訓**

承認済みバージョンの提出トレインが閉じた場合、ビルド番号だけ増やしてもアップロードできない。

**今後の対策**

- `CFBundleShortVersionString` と `CFBundleVersion` を区別する。
- 新しいApp StoreバージョンではMarketing Versionを更新する。
- 同じバージョンの新しいビルドではBuild Numberを増やす。
- App Store Connect側のバージョン状態を確認する。
- CI/CDでバージョン番号の整合性を検証する。

#### 2.9 dSYMのアップロード警告

**発生した問題**

GoogleMobileAds.frameworkのdSYMがArchiveに含まれておらず、シンボルのアップロードに失敗した。

**今後の対策**

- ReleaseビルドのDebug Information Formatを確認する。
- SDKのdSYM提供状況を確認する。
- Archiveに必要なシンボルが含まれているか検証する。
- クラッシュ解析への影響を確認する。
- dSYM警告と、アプリ本体のアップロード失敗を区別して対処する。

### 3. App Store Connectのメタデータ

Futoの経験に加え、今後のアプリでは以下を提出前に一括確認すること。

- アプリ名、サブタイトル、説明文
- キーワード
- スクリーンショット
- アプリアイコン
- Copyright
- Content Rights Information
- 年齢レーティング
- Privacy Policy URL
- Support URL
- 必要に応じた利用規約URL
- App Privacyの申告
- 課金商品の情報
- 審査用アクセス情報
- Review Notes
- 日本語・英語のローカライズ

**重要**

URLは登録するだけでは不十分。

すべてのURLについて、HTTPSで正常にアクセスでき、404にならず、実際に目的の内容が表示されることを確認する。

### 4. 広告SDK・AdMobの教訓

FutoではGoogle Mobile Adsを採用した。

広告SDKを利用する場合、広告表示の実装だけでは不十分である。

**確認事項**

- SDKとPrivacy Manifestの整合性
- App Tracking Transparencyへの対応要否
- GDPRなど地域別の同意管理
- App Storeのプライバシー申告
- 広告表示位置とユーザー体験
- 広告削除課金との連携
- テスト広告と本番広告の切り替え
- 広告表示失敗時の動作
- `app-ads.txt` の公開と認証

**app-ads.txtの教訓**

Futoでは当初、GitHub Pagesのプロジェクト配下にファイルを置いていたが、AdMobが参照するドメイン直下には存在しなかった。

そのため、開発者Webサイトのホストに対応するルートパスへ配置を修正した。

今後は、AdMobが参照するドメインと実際の公開先を照合すること。

なお、app-ads.txtの認証とApp Store審査は別の手続きである。

### 5. 課金実装の検証

StoreKitの単体テストに成功しても、実際のApp Storeでの購入動作が保証されるわけではない。

最低限、以下を確認する。

- 商品IDの一致
- App Store Connectの商品登録状態
- 商品価格の表示
- 購入処理
- 購入失敗時の処理
- 購入の復元
- 再インストール後の権利復元
- 消耗型・非消耗型の適切な処理
- 広告削除など購入特典の即時反映
- Sandboxでの実機テスト
- 必要な課金商品の審査提出

**注意**

初めて非消耗型課金を提出する場合など、アプリの新しいバージョンと一緒に課金商品を提出する必要があるケースがある。

App Store Connect上の商品作成だけで、販売開始できるとは限らない。

### 7. 開発エージェントへの実行指示

今後のiOSアプリ開発では、以下の方針を必ず守ること。

**1. 審査要件を後回しにしない**

アプリの主要機能を実装する前に、利用予定のAPI・SDK・課金方式がApp Store審査に適合するか調査する。

**2. 公式資料を優先する**

Apple Developer Documentation、App Review Guidelines、App Store Connect Helpを優先して参照する。

**3. 審査リスクを早期に報告する**

権限、プライバシー、広告、課金、ログイン、ユーザー生成コンテンツなどについて、審査リスクが見つかった時点で報告する。

**4. 審査向けの不自然な実装を避ける**

審査を通すためだけの虚偽の設定や、実際の機能と異なる説明を行わない。

**5. 配布用ビルドで検証する**

Debugビルドだけでなく、Distribution署名済みのReleaseビルドで確認する。

**6. アプリとApp Store Connectを一体として扱う**

コードだけでなく、メタデータ、課金商品、プライバシー申告、サポートページも成果物として扱う。

**7. 検証結果を明確に区別する**

次の状態を混同しない。

- 実装済み
- 単体テスト成功
- シミュレータで確認済み
- 実機で確認済み
- Sandboxで確認済み
- App Store Connectで設定済み
- Apple審査承認済み

**8. 提出前に審査監査を実施する**

実装完了後、Appleの審査担当者の視点から、アプリ全体を点検する。

問題を発見した場合は、重要度、原因、修正方法、再検証方法を報告する。

### 8. 最終的な教訓

Futoの開発では、機能実装そのものよりも、Appleの配布要件、課金ポリシー、プライバシー申告、審査用の説明などが公開時の障害となった。

特に次の5点を重視する。

1. **課金方式は最初に設計する。** 後から変更すると影響範囲が大きい。
2. **権限と署名は配布構成で確認する。** Debugでの成功は十分ではない。
3. **SDKのプライバシー要件を理解する。** 導入しただけで申告義務が変わる場合がある。
4. **App Store Connectも開発対象と考える。** メタデータの不備でも公開できない。
5. **審査担当者が実際に試せることを保証する。** 機能が存在するだけでは十分ではない。

**完成の定義は、コードの実装完了ではなく、実機検証・配布署名・プライバシー・課金・メタデータ・審査対応まで整った状態とする。**

このガイドラインを新規iOSプロジェクトの開発方針として適用すること。
